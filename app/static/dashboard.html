Where taint analysis fits
Analysis/detection and runtime enforcement are related but distinct stages.
PIPELINE EXPLAINER
1Taint sources

GraphQL variables and object identifiers are treated as attacker-controllable inputs when the source model marks them untrusted.

2Propagation

The analysis follows tainted values through parsed arguments, variables and nested query paths.

3Relationship / graph

Transfer and security-graph logic represent how an input reaches an object or relationship being accessed.

4Authorization reasoning

The authorization-aware candidate checks ownership and role context; taint alone is not proof of BOLA.

5Runtime enforcement

The security middleware and resolver-level ownership checks allow, deny or filter access. Audit records summarize these decisions.

ⓘ
Data source clarification

The per-request flow above uses the actual taint source tracker, parsed object paths, ownership lookup, the existing policy engine in read-only replay, and the observed HTTP/GraphQL response. It does not claim to be a whole-program taint trace or to reveal child objects the resolver deliberately omitted.

CRITICAL SCIENTIFIC NOTICE
⚠ No ML Superiority Claim

In synthetic benchmarks where authorization denials and cross-owner attempts are observable by the gateway, the multi-factor deterministic rule baseline achieved 100% accuracy, outperforming the XGBoost classifier (99.20% accuracy with 8 false negatives). Machine learning models should not be deployed as replacements for authoritative policy checks.

🛡 Strict Zero-Trust Enforcement Boundary

The behavioural ML model is strictly an offline telemetry observer and NEVER overrides PolicyEngine or RuntimeObjectAuthorizationExtension allow/deny decisions. The vulnerable /graphql-insecure endpoint is isolated for controlled comparison only.
