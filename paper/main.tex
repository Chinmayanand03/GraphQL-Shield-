\begin{abstract}
Broken Object Level Authorization (BOLA) is the top risk in the OWASP API Security Top~10, and GraphQL makes it harder to stop: one request can reach an object by identifier, through nested lookups, fragments, variables and batches, or through relationship fields that never name the object. We present GraphQL-Shield, which enforces object ownership at two independent points: a schema-aware layer that checks every identifier it can resolve before execution, and an execution-time layer that checks every object resolvers return and every mutation target the engine coerces. The second layer records each object the first never evaluated, so the gateway measures its own pre-execution coverage. We test this evidence by fault injection: 17 realistic bugs planted in the first layer, each run on 5 seeds of 1,000 composed requests. The evidence revealed all 17 and raised no alarm on the unmodified layer. A one-line rule over the evidence predicted the affected requests with mean F1 0.966; logistic regression and XGBoost both named the broken construct first for all 14 faults our features can express, and XGBoost was no better than the simple models. We state four security properties and check them with property-based testing, close four leak channels the tests exposed (an existence oracle, objects behind interfaces and unions, aggregate fields, and a refused folder deletion), measure no timing difference between foreign and missing objects, and run the same layers on Strawberry, plain graphql-core, Graphene and Ariadne. On the same schema and 13 attacks, graphql-shield also leaks nothing but loses an owner's own data to GraphQL null propagation; GraphQL-Shield loses none, but a type left out of its configuration leaks up to 9 of 13 attacks.
\end{abstract}

\section{Introduction}

An API has a BOLA flaw when it returns or changes an object without checking that the caller may access it. OWASP ranks it first among API risks (API1:2023)~\cite{owasp2023}. It is hard to detect because a BOLA request is ordinary authenticated traffic: the only difference is whose object it names.

GraphQL widens this attack surface. A REST endpoint usually takes one identifier in its path; a GraphQL request can name many objects at any depth and can reach objects without naming them. A caller who owns a folder can list its \code{children}, including a document owned by someone else, and no identifier for that document appears in the query. The same identifier can also arrive as a literal, a variable, a variable's default value, inside a named or inline fragment, under an alias, or in one operation of a batch.

Two families of defence exist, and each misses something. Checks that analyse the query before execution see only the identifiers written in it, so relationship traversal is invisible to them. Checks written into each resolver see every object but must be written and maintained field by field. GraphQL-Shield combines both and uses the second to audit the first. Our contributions are:
\begin{enumerate}
\item \textbf{Dual-layer enforcement with cross-layer evidence.} A pre-execution layer and an execution-time layer enforce ownership independently, configured from the schema and a small ownership map. The second records every object the first never evaluated, which turns defence in depth into a coverage measurement.
\item \textbf{A fault-injection evaluation of that evidence.} We plant 17 bugs in the pre-execution layer and measure detection, prediction and localisation. The evidence detects every fault; simple models over it are as good as gradient boosting.
\item \textbf{Stated properties and closed leak channels.} We define safety, non-interference, write safety and availability, check them on generated data and requests, show they fail with protection off, and fix four channels that returned or revealed foreign data in an earlier version.
\item \textbf{Portability and comparison.} The same layers run on four Python GraphQL frameworks and a second, unrelated application. We compare with graphql-shield on the same schema, including configuration mistakes, and report latency with confidence intervals.
\end{enumerate}

\section{Background}

\textbf{GraphQL execution.} A server parses a request, validates it against a typed schema, and calls a resolver for each selected field, top down~\cite{hartig2018}. Arguments are coerced first: variables are substituted, missing variables take their declared defaults, and fragments, aliases and \code{@include}/\code{@skip} directives are expanded. A defence that reads the query text sees the request before coercion; a defence inside the engine sees the values resolvers receive and return.

\textbf{Global identifiers and type confusion.} Many GraphQL APIs use Relay-style opaque identifiers, typically base64 of \code{Type:id}. A resolver that decodes one without checking its type can be handed an identifier of one type where another is expected; Saleor's CVE-2022-39275 is an instance~\cite{cve202239275}.

\textbf{Abstract types.} A field typed as an interface or union (\code{node(id:)}, a search result) returns objects of several concrete types. A check that reads only the declared return type sees no owned type there.

\textbf{Null propagation.} When a non-null field raises an error, GraphQL nulls its nearest nullable ancestor~\cite{graphqlspec}. In a list typed \code{[T!]!}, denying one item cannot null that item alone, so the error nulls the parent object, and the caller's own objects disappear with it.

\section{Related Work}

We found no prior work that enforces BOLA in GraphQL at two layers and uses one layer to measure the other's coverage.

\textbf{BOLA detection by testing.} GraphQLer builds a dependency graph from introspection, chains queries and mutations, and replays requests as other users~\cite{graphqler}. AuthProbe tests REST APIs from an OpenAPI specification with multiple identities~\cite{authprobe}, and a Colored Petri Net approach derives attack models from OpenAPI specifications~\cite{petrinet}. These are test-time tools, two of them for REST. GraphQL-Shield is a runtime defence such tools can evaluate.

\textbf{BOLA enforcement and analysis.} BolaZ combines CodeQL taint tracking with runtime authorization checks in Spring Boot services~\cite{bolaz}; it shares our view that static analysis needs a runtime backstop but targets Java REST services and does not use one layer to measure the other. Lambers et al.\ define taint analysis for graph APIs aimed at broken access control~\cite{lambers2026}, a static complement to our runtime checks.

\textbf{GraphQL authorization and query analysis.} graphql-shield attaches permission rules to types and fields as resolver middleware~\cite{graphqlshieldlib}; it is the per-field approach we compare against. Formal semantics~\cite{hartig2018}, static cost analysis~\cite{cha2020} and empirical schema studies~\cite{wittern2019} underpin depth and cost limits, which bound how expensive a query is, not whose objects it reaches.

\textbf{Foundations.} Layer~2 is a reference monitor~\cite{anderson1972} that mediates every returned object, following complete mediation and fail-safe defaults~\cite{saltzer1975}. Our non-interference property follows Goguen and Meseguer~\cite{goguen1982}. Comparing two layers' decisions is a form of differential testing~\cite{mckeeman1998}, planting bugs to judge a detector follows mutation testing~\cite{jia2011}, and we check properties as in QuickCheck~\cite{quickcheck} using Hypothesis~\cite{hypothesis}. Turning automatically produced records into training labels resembles weak supervision~\cite{snorkel}. A taxonomy of over 100 bug-bounty BOLA disclosures includes GraphQL global-identifier leakage~\cite{bolataxonomy}.

\section{Threat Model and Properties}

The attacker is an authenticated user who wants to read or change objects owned by someone else. They hold a valid token for their own account, can send any syntactically valid request, know or can guess other users' identifiers, and can read the schema. Authentication is sound and the owner lookup is trusted: ownership comes from the data store, never from client input or from the object a resolver returns. Resolvers may contain no authorization checks. An owned object is accessible to its owner and to administrators, and objects reached through relationships are checked individually: owning a parent grants nothing about its children. Out of scope are authentication flaws, function-level authorization, injection, denial of service beyond the depth, alias, token and batch limits we apply, timing channels other than the foreign-versus-missing comparison we measure, and policies richer than owner-or-administrator.

For a non-administrator caller $u$ and any request $q$ we require:
\begin{description}
\item[P1 Safety.] The response to $q$ contains no object $u$ does not own.
\item[P2 Non-interference.] Changing only objects $u$ does not own (their content, existence, or children placed under $u$'s folders) does not change the response to $q$.
\item[P3 Write safety.] $q$ changes the owner or content of no object $u$ does not own, and deletes none.
\item[P4 Availability.] If $q$ names only objects $u$ owns, they are returned.
\end{description}
P2 is stronger than P1: it rules out answers that reveal foreign data indirectly, such as an error that differs for a foreign object and a missing one, or a count that includes foreign children.

\subsection{Per-application configuration}
A \code{ShieldConfig} describes the protected application: its schema; which object types are owned, each mapped to an ownership key; an owner-lookup function from (key, identifier) to owner, optionally with a batched form; the arguments that carry identifiers and a decoder for them (for example, Relay global identifiers); targets for mutations whose return type does not reveal what they change; and aggregate fields, such as a child count, that summarise owned objects. Everything else is derived from the schema. The demo application needs two owned types, one mutation entry (\code{deleteResource} returns \code{Boolean}), one aggregate entry and its owner lookup.

At startup a lint pass compares the configuration with the schema. It reports object types not configured as owned that have an owner-like field (\code{ownerId}, \code{author}, \code{createdBy}, \ldots) or a field of an owned type, and scalar fields on owned types named like counts or totals (\code{childrenCount}, \code{hasChildren}) that are not declared as aggregates. Independently of naming, it also reports every root query that fetches a single object of a type by identifier when that type is neither owned nor declared public, since a per-user lookup is the usual sign of an owned type. Removing any one of the five owned types across our two applications produces a finding for that type, and the complete configurations produce none. The lint remains a heuristic: a type with an unusually named owner field that is reachable only through relationships is not reported.

\subsection{Layer 1: schema-aware pre-execution gate}
Layer 1 parses the request before the engine runs and walks it against the schema. For every field with an identifier argument it takes the object type from the schema---the owned type the field returns, the type embedded in a global identifier when the field returns an interface or union, or a root mutation's configured target---rather than from the field's name. It resolves values as the engine will: literals, variables, declared defaults, lists, named and inline fragments, aliases, and each operation of a batch. A global identifier whose embedded type differs from the expected type is checked as both. One denial rejects the whole request with HTTP 403, so a write never starts.

\subsection{Layer 2: execution-time guard}
Layer 2 runs inside the engine as graphql-core middleware or a Strawberry extension. Before a root mutation's resolver runs, it checks the target argument the engine coerced; a denial raises an error and the resolver never executes. After each resolver returns, it decides whether the value is an owned object from the field's GraphQL type, not the value's class, so it works with typed objects, dictionaries or ORM rows. For an interface or union it resolves the concrete type the way the engine does (\code{\_\_typename}, \code{resolve\_type} or \code{is\_type\_of}). A denied single object becomes \code{null}; a denied list item is removed before non-null types are enforced, so the caller keeps their own items. A list is checked with one batched owner lookup and its decisions are written in one audit transaction. A declared aggregate field is answered by Layer 2 itself as the number of related objects the caller may see. A mutation with no derivable or configured target is denied unless explicitly listed as unguarded.

\subsection{Uniform denials}
Every denial a non-administrator sees carries the same reason, \code{ACCESS\_DENIED}, whether the object belongs to someone else or does not exist; the exact reason and risk score are kept only in the audit log. An earlier version returned \code{OWNERSHIP\_MISMATCH} or \code{OBJECT\_NOT\_FOUND}, and its request explainer returned the owner's identifier, which together let any user enumerate which objects exist and who owns them. Denials also take the same time: when a lookup by identifier finds nothing, Layer~2 still performs the owner lookup, policy decision and audit write it performs for a foreign object.

\subsection{Cross-layer evidence and the advisory predictor}
Layer 1 marks every (type, identifier) it evaluated. Layer 2 writes an audit record only for objects Layer 1 never marked, so each such record is direct evidence of a Layer 1 coverage gap, and no decision is counted twice. When Layer 2 also denies such an object it records a blind-spot event: an attack only Layer 2 stopped. The audit log is hash-chained, so a deleted or edited record is detectable.

The evidence labels requests without manual effort. For each request Layer 1 allows we compute 17 structural features available before execution: depth, field count, relationship fields and chain depth, identifier arguments and how many Layer 1 resolved, nested lookups, variables and defaults, fragments, aliases, directives, batch size, mutation flag and caller role. The features never include ownership data or outcomes. An XGBoost classifier~\cite{xgboost} (120 trees, depth 4) predicts whether a request will reach objects Layer 1 cannot see, and SHAP contributions~\cite{shap} rank the features behind each prediction. At runtime the score is advisory: it is recorded with later blind-spot events and never changes a decision.

\section{Implementation}

GraphQL-Shield is written in Python on FastAPI and graphql-core~3.3, with SQLite (write-ahead logging) for ownership data and audit records. Layer~1 is a dependency on the protected route; Layer~2 is \code{OwnershipMiddleware(config)} for any graphql-core server or a Strawberry extension. Every request is limited to depth 10, 15 aliases, 2,000 tokens and 5 batched operations. Database connections are pooled, parsed queries are cached, and the advisory score is cached per feature vector. The test suite has 392 tests.

We evaluate on two applications. The \emph{demo} application (Strawberry, code-first) has users, documents and folders with integer identifiers. The \emph{clinic} application shares no code with it: a schema-first SDL on plain graphql-core, dictionary resolvers, Relay global identifiers, and patients, records and prescriptions with independent owners. In both, resolvers contain no authorization checks, and each exposes an unprotected endpoint used only as a baseline. To test framework independence we also protect small Graphene (Relay \code{Node}, lists, mutations) and Ariadne (schema-first) applications with the same middleware and configuration type.

\section{Evaluation}

We address five questions. \textbf{RQ1:} does each layer stop BOLA alone, and do both together? \textbf{RQ2:} does the cross-layer evidence reveal faults in Layer~1, and what is needed to use it? \textbf{RQ3:} do the stated properties hold? \textbf{RQ4:} how does the approach compare with per-field rules, including under configuration mistakes? \textbf{RQ5:} what does enforcement cost? All experiments run in-process on temporary seeded databases on one Windows laptop with Python~3.13. Deterministic experiments report counts; randomised ones report the mean and spread over seeds.

\subsection{RQ1: Layer ablation}\label{sec:ablation}
Table~\ref{tab:ablation} runs six attacks by one user against another user's objects under each layer combination. \subsection{RQ2: Cross-layer evidence as a fault detector}\label{sec:faults}

\textbf{One discovery.} We generated 4,000 varied requests from four callers and labelled them from Layer~2's evidence. Layer~1 ignored variables' declared default values, so \code{query(\$id: Int = 102)} sent without variables reached object 102 unchecked. All 585 such requests were coverage gaps and 263 were attacks stopped only by Layer~2. The hand-written rule for Layer~1's documented blind spot, ``flag requests with a relationship field'', reached F1 0.639 and caught 22.8\% of these attacks; the model reached F1 1.000. After the fix, attacks reaching only Layer~2 fell from 401 to 138, the remaining gaps were relationship traversal, and the rule matched the model (F1 0.996 for both). Over five further seeds of 2,000 requests the model and the rule tied at F1 $0.992\pm0.006$.

\textbf{Fault injection.} One discovery is an anecdote, so we measured the evidence systematically. We wrote 17 faults a developer could plausibly introduce into Layer~1 (Table~\ref{tab:faults}), each patched into its source at load time, and ran each fault and an unmodified control on five seeds of 1,000 requests with Layer~2 on. Requests are composed from independent constructs---identifier source (literal, variable, default, list), wrapper (alias, directive, named or inline fragment, nested fragment), location (root, nested lookup, relationship), shape (single operation or batch) and operation (query or mutation)---so a test request is not a copy of a training one. We ask three things of each fault. \emph{Detection:} does the evidence contain gaps the known relationship blind spot does not explain? \emph{Prediction:} on a held-out 30\%, which requests will have gaps? \emph{Localisation:} does a method's top-ranked feature, among gaps the relationship rule does not explain, name the broken construct?

The faults cover ignored variables, ignored defaults (everywhere or only in mutations), skipped named, nested or untyped inline fragments, skipped aliased or directive-bearing fields, nested lookups skipped or only the first visited, fragments handled only at the root, only the first operation, root field or batch operation checked, mutation targets skipped, and the user type skipped. It fails only where the fault makes Layer~1 believe it resolved an identifier it skipped (\code{first\_batch\_operation\_only}, F1 0.733), which the learned models handle. Learned models did not beat simple ones: XGBoost on structural features (0.967) tied logistic regression (0.968), and adding Layer~1's resolution count raised XGBoost to 0.978. The lesson is that the contribution is the evidence, not the model. A gateway with two layers can detect a broken first layer from its own logs, and a linear model or a one-line rule extracts most of the value.

\subsection{RQ3: Properties and leak channels}
We check P1--P4 with Hypothesis~\cite{hypothesis}. Each example draws a world---owners for three folders and six documents among three users, and a parent for each document---a caller, and a request composed as in Section~\ref{sec:faults}; each property runs 120 examples. P2 compares the response in two worlds that agree on the caller's objects and differ arbitrarily in everyone else's. All four properties hold. With both layers off, each property fails, so the tests can detect a violation.

Writing P2 exposed four channels through which an earlier version revealed foreign data, all now closed. \emph{Existence oracle:} Layer~1, Layer~2 and the explainer reported different reasons for a foreign object and a missing one, and the explainer returned the owner's identifier; responses are now identical apart from the requested identifier. \emph{Abstract types:} Layer~2 read only the declared return type, so \code{node(id:2)} or a union search returned a foreign object's content; it now resolves the concrete type. \emph{Aggregates:} \code{childrenCount} counted foreign children, and was protected only by a hand-written check in its resolver; Layer~2 now answers declared aggregates from the visible objects. \emph{Refused deletion:} deleting a folder that held a hidden foreign child failed on the foreign-key constraint, revealing the child; a deleted folder's children now move to the top level, keeping their owner and content, so the response no longer depends on them.

\textbf{Timing.} Identical responses can still differ in time. For each of four settings we sent 1,500 interleaved pairs of requests for a foreign object and a missing one in random order, and compared the medians with a bootstrap 95\% interval and a Mann--Whitney test (Table~\ref{tab:timing}). With Layer~2 alone, a foreign read took 0.352\,ms longer than a missing one (CI [0.193, 0.554], $p=2\times10^{-8}$), because a lookup that found nothing skipped the check. After Layer~2 began checking missing lookups too, no setting showed a difference: every interval contains zero and every $p\geq0.68$. The measurement is in-process; its resolution, about 0.1\,ms, bounds what it can rule out.

Both systems stop all 13 attacks when fully configured. graphql-shield's failure is availability: in \code{children: [ResourceType!]!}, denying the one foreign child cannot null that item, so the error nulls the whole folder and its owner loses their own two documents. Layer~2 removes the item before nullability is enforced. Under configuration mistakes neither approach dominates (Table~\ref{tab:comparison}). GraphQL-Shield fails closed on mutations, but an owned type left out is a single point of failure that leaks up to 9 of 13 attacks; the startup lint reports such omissions. graphql-shield's overlapping rules tolerate one missing read rule, but a missing mutation rule executes the write under its default allow fallback, and its deny fallback blocks legitimate requests instead.

\subsection{RQ5: Latency}
All configurations of one request type are timed in the same run and interleaved: after 30 warm-up requests, each of 10 repeats times 100 requests of every configuration, in a fresh random order, after 10 untimed ones. Drift on the machine then affects every configuration alike, and the overhead is estimated from the per-repeat difference to the unprotected endpoint, with a 95\% confidence interval ($t$, 9 degrees of freedom). An earlier, sequential version of this benchmark produced overheads that changed sign between runs.

With both layers, an owned lookup took 10.4\,ms against 9.4\,ms unprotected, a paired overhead of $+0.99$\,ms (CI $[-0.36, 2.35]$); a relationship query $+0.86$\,ms ($[0.32, 1.40]$); and an update $+0.00$\,ms ($[-1.28, 1.29]$). Protection therefore costs about 1\,ms per request on this machine, and at most 2.4\,ms. Three fixes found by profiling brought it there. Pooling database connections cut both-layer latency 3.1 to 6.0 times (Fig.~\ref{fig:latency}). The risk score ran an unindexed count over the whole audit log for every checked object, so latency grew with the log; an index and an existence probe made it constant. Finally, the advisory predictor cost about 4.4\,ms of Layer~1's 5.3\,ms, mostly starting XGBoost's thread pool for a one-row prediction; scoring on one thread and caching the probability per feature vector, together with caching parsed queries, removed nearly all of it.

\section{Discussion and Limitations}

\textbf{External validity.} Both applications, the Graphene and Ariadne examples, the injected faults and all attack scenarios were written by the authors. The results show the mechanism works on these applications, not that it generalises. We did not evaluate on third-party applications or with independently written attacks, and we did not run black-box testers such as GraphQLer against the gateway; both are the most important future work.

\textbf{Synthetic traffic.} The predictor and the fault-injection study use generated requests from a small world. In this world a coverage gap follows almost entirely from query structure, so F1 near 1.0 reflects an easy target, not real-world accuracy. The fault study measures whether the evidence carries the signal, not how often real Layer~1 bugs occur.

\textbf{Configuration.} An owned type left out is unprotected by both layers. The lint narrows this, but it combines naming with lookups by identifier and can still miss a type reached only through relationships. Only owner-or-administrator policies are supported; sharing, teams and attribute-based rules fit into Layer~2's per-object check but are not implemented.

\textbf{Residual channels.} The timing measurement is in-process; over a network an attacker averages more samples but also faces more noise, which we did not model. Moving a deleted folder's foreign children to the top level changes where they are filed, a choice the folder's owner makes for their own folder, but their owners may not expect it.

\textbf{Measurement.} Latency was measured in-process on a laptop; network latency, absent here, would make the roughly 1\,ms overhead relatively smaller. graphql-shield was reimplemented on a copy of our schema in its documented style; other rule sets could perform differently, and its Node.js latency is not comparable in absolute terms with our Python numbers.

\section{Conclusion}

Enforcing GraphQL object ownership at two independent points stops BOLA in every form we tested and lets a gateway measure its own coverage. A pre-execution layer alone misses objects reached through relationships; an execution-time layer catches them and records each object the first layer never saw. Planting 17 bugs in the first layer showed that this record detects every one, that a one-line rule over it predicts the affected requests, and that simple models name the broken construct as reliably as gradient boosting. Stating non-interference exposed and closed four leak channels in our own system, and the remaining responses show no timing difference. The layers are configured from the schema and a small ownership map, run on four Python GraphQL frameworks, and avoid the availability loss per-field rules suffer under null propagation. Evaluating on third-party applications with independently written attacks is the next step.
